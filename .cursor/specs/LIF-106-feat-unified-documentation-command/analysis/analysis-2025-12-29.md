# LIF-106 Spec Analysis Report

**Date**: 2025-12-29
**Analyzer**: OmO
**Spec Version**: Ready for Planning (initial)

---

## Executive Summary

The current LIF-106 spec provides a solid foundation for the unified `/documentation` command, but has **9 critical gaps** that need to be addressed before planning. Most significantly:

1. **No flag/subcommand definition** despite mentioning "optional flags" in FR-1
2. **No dynamic scaling model** for agent counts (fixed at 3-5 instead of "dozens+")
3. **No clarification workflow** for broad/ambiguous requests
4. **Project-context.yaml not explicitly in scope**

---

## Critical Gaps (Must Fix Before Planning)

### GAP-1: Missing Flags/Subcommands Definition

**Severity**: CRITICAL

**Current State**: FR-1 says "accepting optional flags to control behavior" but never defines them.

**Required**: Define explicit flags like existing commands have.

**Recommended Flags**:
| Flag | Description | Example |
|------|-------------|---------|
| `--docs-only` | Only update public docs (README, guides, API) | `/documentation --docs-only` |
| `--memory-only` | Only update memory files (constitution, architecture, etc.) | `/documentation --memory-only` |
| `--context-only` | Only update project-context.yaml | `/documentation --context-only` |
| `--inline-only` | Only update inline code comments | `/documentation --inline-only` |
| `--validate-only` | Only run validation, no writes | `/documentation --validate-only` |
| `--scope <path>` | Limit to specific file/directory | `/documentation --scope src/tools/` |
| `--diff-based` | Only document what changed in current branch | `/documentation --diff-based` |
| `--full` | Explicit full review (default behavior) | `/documentation --full` |
| `--parallel <n>` | Max parallel agents (default: unlimited) | `/documentation --parallel 20` |
| `--dry-run` | Show what would be done, don't execute | `/documentation --dry-run` |

**Impact**: Without flags, users cannot do targeted documentation work.

---

### GAP-2: No Dynamic Agent Scaling Model

**Severity**: CRITICAL

**Current State**: Spec says "3 documentation review agents" and "3-5 code review agents" (fixed numbers).

**User Requirement**: "kick off dozens or more agents" for large scope.

**Required**: Dynamic scaling based on scope.

**Recommended Model**:
```
SCOPE DETECTION:
- Single file → 1-2 agents
- Single module → 3-5 agents
- Multiple modules → 5-10 agents
- Full project → 10-30+ agents
- Full project + validation → 30-50+ agents

AGENT ALLOCATION:
- Per unique doc type: 1-3 dedicated agents
- Per major code module: 1-2 review agents
- Validation: 2-3 parallel validators
- Synthesis: 1 manager collecting all results
```

---

### GAP-3: No Clarification Workflow

**Severity**: CRITICAL

**Current State**: No mechanism to ask clarifying questions for broad requests.

**User Requirement**: "if the users request is really broad then our command could clarify by asking some questions first"

**Required**: Add clarification workflow before execution.

**Recommended Flow**:
```
1. Parse user request
2. Detect scope ambiguity:
   - No specific target mentioned
   - Multiple possible interpretations
   - Very broad scope keywords ("everything", "all", "full review")
3. If ambiguous AND scope is large:
   - Present clarifying questions
   - Wait for response
   - Proceed with refined scope
4. If clear OR scope is small:
   - Proceed directly with smart defaults
```

**Clarifying Questions Examples**:
- "You want to document 'everything'. Focus on: [a] What changed this PR [b] Full project [c] Specific area?"
- "Full project has 150 modules. Prioritize: [a] Core modules only [b] Public APIs [c] Everything (will spawn 30+ agents)?"
- "Should I include inline code comments? [y/n]"

### GAP-4: Project-Context.yaml Not Explicitly In Scope

**Severity**: HIGH

**Current State**: Memory files (constitution.md, etc.) are in scope, but `.opencode/project-context.yaml` is not mentioned.

**Required**: Explicitly add to scope OR explicitly exclude with rationale.

**Recommendation**: ADD to scope under memory/context management.

**Why**: It's project context used by agents - logical fit for unified command.

---

### GAP-5: No Smart Auto-Detection

**Severity**: HIGH

**Current State**: No auto-detection of user intent like `/update-context` has.

**Reference**: `/update-context` has excellent auto-detection:
- No memory files → init
- User provides content → update
- User asks to view → view
- User mentions validation → validate

**Required**: Add similar auto-detection for `/documentation`.

**Recommended Detection**:
| Context | Detected Intent | Behavior |
|---------|-----------------|----------|
| No docs exist | Initialize | Create foundational docs |
| User says "update X" | Targeted update | Focus on X only |
| User says "review" | Validation | Validate all, suggest updates |
| User provides diff/PR | Diff-based | Document what changed |
| No specific target | Full review | Spawn many agents |
| User mentions feature | Feature docs | Scope to feature |

---

### GAP-6: No Anti-Bloat Guardrails

**Severity**: HIGH

**Current State**: Risk table mentions "Memory system bloat" but no guardrails defined.

**Reference**: `/update-context` has excellent guardrails:
- File size limits per file type
- Entry word limits
- Deduplication checks
- Priority scoring

**Required**: Inherit these guardrails for memory file operations.

### GAP-7: Missing User Story for Granular Control

**Severity**: MEDIUM

**Current State**: No user story capturing the flags/granular control need.

**Required**: Add US-7.

**Recommended**:
```markdown
### US-7: As a developer
I want to control which documentation types get updated
So that I can run quick, targeted updates without full project review

**Acceptance Criteria:**
- [ ] Flags available for docs-only, memory-only, inline-only, etc.
- [ ] Default (no flags) runs full comprehensive review
- [ ] Flags can be combined (e.g., --docs-only --scope src/tools/)
- [ ] --dry-run shows what would happen without executing
```

### GAP-8: Missing User Story for Clarification

**Severity**: MEDIUM

**Current State**: No user story for the clarification workflow.

**Required**: Add US-8.

**Recommended**:
```markdown
### US-8: As a developer with a broad request
I want the system to ask clarifying questions before spawning many agents
So that I don't waste resources on unwanted documentation work

**Acceptance Criteria:**
- [ ] System detects ambiguous/broad requests
- [ ] Presents relevant clarifying questions
- [ ] Waits for user response before proceeding
- [ ] Offers sensible defaults if user wants to skip questions
- [ ] Questions are context-aware (e.g., knows project has 150 modules)
```
