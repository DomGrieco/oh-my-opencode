## Critical Findings

### C1: `/lsp-check` Should Be a Tool, Not Just a Command

**Finding**: The plan creates `/lsp-check` as a slash command but misses that it should be a proper tool (like `lsp_hover`, `lsp_servers`).

**Impact**: High - Commands cannot be called programmatically by agents. A tool can be used by agents autonomously.

**Recommendation**:
```typescript
// Create as tool in src/tools/lsp/tools.ts
export const lsp_check = tool({
  description: "Validate LSP server installations and health",
  args: {
    language: tool.schema.string().optional(),
    serverId: tool.schema.string().optional(),
  },
  execute: async (args) => { /* ... */ }
})

// ALSO create command that calls the tool
// .opencode/command/lsp-check.md
```

**Evidence**: Oracle agent analysis + LSP tools exploration confirmed this pattern.

---

### C2: Bun Migration Is Lower Risk Than Documented

**Finding**: The existing init-project code uses patterns that are mostly Bun-compatible. Migration is simpler than planned.

**Current Issues (from explore agent)**:
| Pattern | Current | Fix |
|---------|---------|-----|
| `import * as fs from "fs"` | Node.js style | `import { existsSync, readFileSync } from "fs"` |
| `import * as path from "path"` | Node.js style | `import { join, basename } from "path"` |
| `require.main === module` | CommonJS | `import.meta.main` |
| npm commands in generation | Node.js default | Detect bun, use `bun test` |

**Impact**: Medium - Time estimates may be inflated. Phase 3 (3.5h) could be 2-2.5h.

**Recommendation**: Reduce Phase 3 estimate and complexity rating.

---

### C3: First-Run Hook May Conflict with Existing Hooks

**Finding**: The planned first-run detection hook uses `session.created` event, which is already used by:
- `auto-update-checker` - Checks for plugin updates
- `startup-toast` - Shows welcome message
- `rules-injector` - Initializes rule caching

**Impact**: Medium - Multiple hooks showing toasts/messages on startup could overwhelm users.

**Recommendation**: 
1. Integrate first-run check INTO `auto-update-checker` or `startup-toast`
2. OR use a debounced/prioritized notification system
3. Check for existing `.opencode/` BEFORE showing toast (already in plan)

## Important Findings

### I1: Missing LSP Server Installation Commands in Constants

**Finding**: `BUILTIN_SERVERS` in constants.ts only has `command` and `extensions`. Missing:
- Installation command per platform
- Verification command
- Binary name for PATH check
- Recommended flag
- Category

**Current Structure**:
```typescript
export const BUILTIN_SERVERS: Record<string, Omit<LSPServerConfig, "id">> = {
  typescript: {
    command: ["typescript-language-server", "--stdio"],
    extensions: [".ts", ".tsx", ".js", ".jsx", ".mjs", ".cjs", ".mts", ".cts"],
  },
  // Missing: installation, verification, recommended, category
}
```

**Needed Structure**:
```typescript
export const BUILTIN_SERVERS = {
  typescript: {
    command: ["typescript-language-server", "--stdio"],
    extensions: [".ts", ".tsx", ".js", ".jsx", ".mjs", ".cjs", ".mts", ".cts"],
    // NEW fields
    installation: {
      macos: "npm i -g typescript-language-server typescript",
      linux: "npm i -g typescript-language-server typescript",
      windows: "npm i -g typescript-language-server typescript",
    },
    binary: "typescript-language-server",
    verification: "typescript-language-server --version",
    recommended: true,
    priority: 10,
    category: "JavaScript/TypeScript",
  },
}
```

**Impact**: Medium - Affects lsp-check tool and documentation generation. Should be done in Phase 1.

**Recommendation**: Add new task T0.1 in Phase 1: "Enhance BUILTIN_SERVERS constant with installation metadata"

### I3: Metrics Schema Missing Versioning Strategy

**Finding**: The metrics schema has `version: "1.0.0"` but no migration strategy for schema changes.

**Current Schema**:
```typescript
interface OhMyOpenCodeMetrics {
  version: "1.0.0"
  init: { /* ... */ }
  lsp: { /* ... */ }
  projects: [ /* ... */ ]
}
```

**Impact**: Low - Future schema changes could break existing metrics files.

**Recommendation**: Add migration function:
```typescript
function migrateMetrics(data: unknown): OhMyOpenCodeMetrics {
  const version = (data as any)?.version ?? "0.0.0"
  if (version === "1.0.0") return data as OhMyOpenCodeMetrics
  // Handle older versions
  return DEFAULT_METRICS
}
```

### I5: Missing Rollback/Recovery for Init Failures

**Finding**: Edge cases cover backup before modify, but no recovery if init fails midway.

**Scenario**: User runs `/init-project`, it creates partial files, then crashes. User is left with broken state.

**Impact**: Medium - Poor UX on failure.

**Recommendation**: Add atomic operation wrapper:
```typescript
async function atomicInit(projectPath: string, config: InitProjectConfig) {
  const tempDir = `${projectPath}/.opencode-init-temp`
  try {
    // Create all files in temp dir
    await generateAllFiles(tempDir, config)
    // Atomic move to final location
    await moveAtomically(tempDir, `${projectPath}/.opencode`)
  } catch (e) {
    // Clean up temp dir
    await rmdir(tempDir, { recursive: true })
    throw e
  }
}
```

## Edge Cases Analysis

### EC1: Monorepo Structures

**Finding**: Tech detection handles monorepo detection (lerna, pnpm-workspace, turbo, nx, rush) but init flow doesn't have clear monorepo-specific behavior.

**Recommendation**: 
- Detect monorepo type
- Offer per-package vs root-only initialization
- Generate appropriate AGENTS.md for monorepo structure

### EC2: Conflicting LSP Extensions

**Finding**: Multiple servers handle same extensions:
- `.ts`, `.tsx`: typescript, deno, eslint
- `.py`, `.pyi`: basedpyright, pyright, ruff
- `.vue`: vue, eslint

**Current Behavior**: First match wins (via `findServerForExtension`).

**Recommendation**: Add `priority` field to BUILTIN_SERVERS and use highest priority server. Already in plan but needs explicit implementation task.

### EC3: WSL vs Native Windows

**Finding**: Windows users may run in WSL2 or native. PATH and installation commands differ.

**Recommendation**: Add WSL detection:
```typescript
function isWSL(): boolean {
  return existsSync("/proc/version") && 
    readFileSync("/proc/version", "utf-8").toLowerCase().includes("microsoft")
}
```

### EC4: Docker/Devcontainer Environments

**Finding**: In devcontainers, LSP servers may be pre-installed or need container-specific setup.

**Recommendation**: 
- Detect `.devcontainer/` directory
- Note in docs that devcontainer may have different requirements
- Consider `--skip-install-check` flag

### EC5: Metrics File Corruption

**Finding**: No handling for corrupted metrics file.

**Recommendation**: Add try/catch with reset:
```typescript
function readMetrics(): OhMyOpenCodeMetrics {
  try {
    const content = readFileSync(METRICS_PATH, "utf-8")
    return migrateMetrics(JSON.parse(content))
  } catch {
    // Reset to default on corruption
    return DEFAULT_METRICS
  }
}
```

## Appendix A: Codebase Patterns Reference

### Tool Definition Pattern
```typescript
export const tool_name = tool({
  description: "...",
  args: {
    param: tool.schema.string().describe("..."),
  },
  execute: async (args, context) => {
    try {
      // Logic
      return output
    } catch (e) {
      return `Error: ${e instanceof Error ? e.message : String(e)}`
    }
  },
})
```

### Hook Definition Pattern
```typescript
export function createMyHook(ctx: PluginInput) {
  const state = new Map<string, unknown>()
  
  return {
    "tool.execute.after": async (input, output) => {
      // Post-tool logic
    },
    event: async ({ event }) => {
      if (event.type === "session.created") {
        // Session start logic
      }
    },
  }
}
```

```typescript
// Instead of: import * as fs from "fs"

// Instead of: import * as path from "path"
```
